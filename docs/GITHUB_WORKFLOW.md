# Project GitHub workflow

> 역사적 구현 문서: 2026-10-05 사용자 요청으로 이 네이티브 화면의 앱 진입점과 Activity 등록을 제거했다. 현재는 터미널에서 파일·git·gh 도구를 사용한다. 아래 내용은 제거 전 구현과 검증 기록이며 현재 제공 UI가 아니다.

`Z8GitHubActivity.intent(context, projectId)` opens a private native screen. Register it as `exported="false"` and open it explicitly from the workspace. The screen identifies execution as **LOCAL · 프로젝트 Linux CLI → github.com**. GitHub reads, authentication and PR creation require the selected project's installed rootfs, executable `/usr/bin/gh`, and own-prefix PRoot. Public clone needs the same guest and executable `/usr/bin/git`, but not gh or a login. Missing prerequisites link to the project Linux environment screen; if Git alone is ready, a typed-repository clone control remains available. There is no Android/desktop GitHub CLI fallback.

## User flow

Opening or resuming the screen checks local runtime availability, reads the current project’s `origin`, and performs an asynchronous read-only authentication check. Resource queries remain explicit. Authentication status updates in place without disabling repository actions or rebuilding the user’s focused input. The primary view presents the current repository, issues, PRs and Actions; account switching, repository editing, clone and search are grouped in an expandable section.

- **인증 다시 확인** runs authenticated `gh api --hostname github.com --method GET -- user`. Only a valid JSON user object containing a supported login and positive integral account ID establishes success. In the audited gh 2.45 environment, `auth status` can exit zero with `GH_HOST` and no account, so it is no longer used as evidence of authentication. Login-required, permission/rate-limit, network/timeout and invalid-response states remain distinct. Raw auth output and tokens are neither rendered nor persisted.
- **GitHub 로그인** opens the real project PTY through a private app route. The Activity supplies a project identifier, never a command string or URL. The root integration executes the fixed official command `gh auth login --hostname github.com --git-protocol https --web` in that guest and leaves a login shell when it exits. The user completes authentication in the terminal/browser flow and the screen automatically verifies the account when reopened. Unsent fields are persisted before navigating to the terminal.
- A validated GitHub `origin` pre-fills the repository. HTTPS and Git-over-SSH GitHub origins are supported; foreign hosts, credential-bearing HTTPS URLs, queries, control characters and encoded paths never become a displayed repository. A user-entered `owner/repository` also supports repository metadata, open issues, open PRs, and recent Actions runs. Repository search supports a bounded query; selecting a result fills the repository and opens its metadata.
- Issue and PR rows open titles, authors, states and body text. PR details identify their HEAD commit and offer separate **체크 실행** and **커밋 상태** reads. These represent check runs and legacy commit statuses; neither an empty page nor an incomplete subset is presented as an overall passing PR.
- Lists request up to 30 server records per page. REST issue pages can contain PRs, which are filtered out without losing the ability to request the next server page. Lists stop at 100 pages, repository search at GitHub's first 1,000-result range. A full page enables an explicit next request; it is not a claim that more records definitely exist.

The Activity shows loading, missing-runtime, error and prior-result states. Refresh failure leaves the previous result labeled as stale, with its original receipt time. Returning to the Activity also marks existing results stale. Read requests are not polled in the background. Rotation preserves the selected query, repository and page; private response bodies are reloaded on demand rather than written to a bundle or disk cache. User-authored, unsent PR and review fields survive rotation and later navigation through per-project app-private preferences. Remote bodies and authentication output are not cached there.

## Explicit clone into this project

Repository metadata and search-result cards offer **이 프로젝트에 clone**. The typed `owner/repository` field also offers **입력한 저장소 clone**, which needs no preceding gh API read or login check, allowing ordinary anonymous public HTTPS clones. Before presenting the confirmation, a worker validates the selected repository, project guest tools and an empty source directory. Empty means no entries, including dotfiles and dangling symlinks; source paths with symlink ancestors are rejected. The confirmation names the exact GitHub repository, project and `/workspace` destination. Only **clone 시작** accepts the operation.

The confirmation callback immediately acquires a per-project lease and registers the shared worker, so destruction of the Activity's separate read executor cannot discard an accepted operation. The worker rechecks the empty source immediately before launching. This protects against duplicate Activity instances or rotation. Git also performs its normal empty-destination check, covering ordinary changes after the app's check. This is not a cross-process filesystem transaction or a defense against hostile same-UID races.

When gh is installed, clone executes the following fixed argv in the same guest. Only the validated owner/repository segment varies:

```text
/usr/bin/git
  -c credential.https://github.com.helper=
  -c credential.https://github.com.helper=!/usr/bin/gh auth git-credential
  clone --no-recurse-submodules -- https://github.com/OWNER/REPO.git /workspace
```

The per-command GitHub credential helper resets that URL's helper chain and uses this guest's gh account. No token is put in argv, an error message or a new configuration file. Other guest Git configuration remains active, including user-configured clone behavior. The helper command is a constant understood by Git's credential-helper mechanism; repository text is never interpolated into it. Submodules are not recursively fetched.

When gh is absent, both `-c` helper pairs are omitted and the fixed Git clone/verification commands remain available. Clone does not run `gh auth status` or require a successful API read. With an installed but unauthenticated gh, the [v2.45.0 helper implementation](https://github.com/cli/cli/blob/v2.45.0/pkg/cmd/auth/gitcredential/helper.go) returns a silent failure with no credential output when no token exists; its [upstream test](https://github.com/cli/cli/blob/v2.45.0/pkg/cmd/auth/gitcredential/helper_test.go) explicitly covers empty stdout/stderr in that case. The app also sets `GIT_TERMINAL_PROMPT=0`. An ordinary public HTTPS clone can proceed without credentials; private repositories or guest configuration that requires credentials may fail and remain recoverable. Android network acceptance is still a separate test.

This uses Git directly because [gh v2.45.0's clone implementation](https://github.com/cli/cli/blob/v2.45.0/pkg/cmd/repo/clone/clone.go) automatically fetches a fork's parent and changes the default remote, while lacking the newer `--no-upstream` option documented in the [current gh clone manual](https://cli.github.com/manual/gh_repo_clone). The fixed gh credential-helper approach follows the [GitHub CLI authentication implementation](https://github.com/cli/cli/blob/trunk/git/client.go) and [Git credential-helper semantics](https://git-scm.com/docs/gitcredentials), retaining compatibility with the guest's older gh package.

Clone has a 110-second process budget, followed by up to 10 seconds for a real guest `git -C /workspace rev-parse --is-inside-work-tree` check. Both retain 1 MiB stdout/stderr caps; the shared runner also has bounded output-drain cleanup. A successful exit alone is insufficient: the app requires a normal contained `.git` directory, regular `HEAD` and `config` files, an `objects` directory, and a successful `true` response from Git. Empty remote repositories can still pass this worktree check.

Accepted clone, draft-PR and review jobs belong to a shared static worker and continue independently of the Activity. A maximum of two projects can run operations concurrently; each project has one shared lease across clone, draft creation and review submission. A recreated screen attaches to the existing state, and the foreground screen observes that local state without making network requests. Completed states retain no Activity or token. The state is in memory: process death does not preserve the worker or its completion receipt, and never triggers automatic resumption. After interruption, inspect the project's actual files/Git state.

If clone fails, times out or cannot be verified, the UI says its result is partial or unknown. The app performs no recursive cleanup, overwrite or automatic retry; Git itself retains its normal failure behavior. Existing partial files prevent another clone until the user explicitly inspects and resolves them, or chooses a new empty project. The result offers a link to the project Git screen.

## Reviewed Draft PR creation

The typed repository field offers **Draft PR 작성**. Opening the form runs read-only preflight: authenticated `GET user` and `GET repos/OWNER/REPO`. It requires a verified account, the exact readable repository, and a repository that is neither archived nor disabled. Missing or failed read responses stop the flow. This establishes identity and repository access; token scopes and the final right to create a PR are enforced by GitHub when it receives the write.

The form shows repository/account and takes an already-pushed head branch, optional `owner:branch` head syntax, base branch, title and body. Base defaults to the repository's actual default branch. The implementation does not push, infer a branch, or silently create a fork. Branch syntax and encoding are bounded; titles are one line and at most 256 characters; bodies are at most 16 KiB of UTF-8. The full review screen displays the exact repository, account, head → base, Draft status, title and body. Only **검토한 Draft PR 생성** submits the operation.

Immediately before creation, the worker repeats preflight and rejects an account change. It then performs a bounded `GET repos/OWNER/REPO/pulls?state=open&head=OWNER:BRANCH&base=BASE...`, with encoded query values. An existing matching open PR yields `EXISTS` and its verified result without sending POST. Failed, malformed or unexpected duplicate-query data stops the operation instead of allowing a blind write. A plain head branch is qualified with the target repository owner for this duplicate check; an explicit head owner is preserved. GitHub's constraints for unusual same-organization cross-repository heads may still require terminal use when additional API fields are needed.

The write is one fixed `gh api --hostname github.com --method POST ... --input - -- repos/OWNER/REPO/pulls` invocation. JSON containing `title`, `body`, `head`, `base` and `draft: true` travels through stdin with an explicit JSON content type. No title, body or credential is placed in argv or a temporary payload file. See the official [create pull request API](https://docs.github.com/en/rest/pulls/pulls#create-a-pull-request) and [gh API stdin behavior](https://cli.github.com/manual/gh_api).

Each preflight/write subprocess has the same 30-second and 1 MiB bounds as a read. Completed operation states contain repository/head/base, phase and a validated result, not the submitted body or authentication output. Creation is reported only after a successful response identifies an open **draft** PR with the exact base repository, head label and base branch. Its positive number and URL must agree; URLs must be HTTPS on `github.com`, with the matching repository `/pull/NUMBER` path and no user info, explicit port, query, fragment or control characters. Unknown or mismatched output never becomes a clickable or displayed result URL.

A definite API validation/permission rejection becomes `FAILED`; timeout, lost response, execution failure after the POST attempt, or an unverifiable success response becomes `UNKNOWN`. The screen directs the user to check opened PRs before taking another action. There is no automatic retry, replay, or POST on Activity creation/resume. A duplicate-check/creation race is still possible, and this is not an exactly-once protocol. Another process can also change the account or remote state between requests; GitHub remains authoritative.

User-authored unsent form fields are saved in per-project app-private preferences as well as normal Activity instance state. Closing a form, navigating to the terminal, recreation, and rejected or uncertain submissions retain the authored text. A verified CREATED/EXISTS receipt clears the matching PR form. Reopening a form obtains fresh account/repository context. The review must still be explicitly confirmed; neither restored fields nor Activity resume triggers a write. Process death loses the in-memory operation receipt and does not replay submission, so GitHub must be checked before manually retrying an uncertain result.

## Start work from an issue

The issue detail screen offers **이 이슈로 작업 시작**. Read-only preflight verifies that the selected issue repository matches the project’s current GitHub origin and captures fresh Git status. A confirmation names the repository, issue, project’s current branch, and editable branch name (default `issue/NUMBER`). On **브랜치 만들고 열기**, origin is checked again and the existing Git adapter creates/switches the local branch from the inspected HEAD. Its dirty-tree, stale-state and branch-name checks apply. No issue text becomes shell syntax or an AI prompt; no remote branch, issue or comment is created. The result opens the project Git screen.

## PR files and reviewed submissions

PR details provide paginated **변경 파일 · diff** and **리뷰 내역** reads, plus a return-to-PR control. File patches render as selectable monospace text. Absent patches are explicitly labeled as unavailable (for example binary or oversized changes), rather than shown as an empty successful diff. Each page has at most 30 records and the GitHub files endpoint’s 3,000-file ceiling is stated. Review states and author/body text are shown independently of checks. See [list pull request files](https://docs.github.com/en/rest/pulls/pulls#list-pull-requests-files) and [list PR reviews](https://docs.github.com/en/rest/pulls/reviews#list-reviews-for-a-pull-request).

**이 HEAD에 리뷰 작성** obtains the authenticated account and presents COMMENT, APPROVE or REQUEST_CHANGES with a body bounded to 16 KiB UTF-8. COMMENT and REQUEST_CHANGES require a nonempty body. Unsent bodies and decision selection are stored per project/repository/PR. The preview names the exact repository, PR, account, inspected HEAD, decision and body. Only **검토한 리뷰 제출** accepts the operation.

The shared worker verifies the current account and re-reads the PR immediately before POST; a changed account, closed PR or changed HEAD stops before writing. Submission sends one fixed REST reviews endpoint with `commit_id`, `event` and `body` through stdin. The response must contain a positive integral review ID, matching decision state, account, commit and API PR URL before success is shown. Definite API rejection differs from an uncertain outcome; uncertain outcomes direct the user to review history and never retry automatically. A state read or screen recreation never resends the POST. This uses the official [create-review API](https://docs.github.com/en/rest/pulls/reviews#create-a-review-for-a-pull-request). It is a whole-PR review; inline line comments, merge, marking a draft ready, reviewer assignment and Actions reruns remain terminal/GitHub workflows.

## Guest and protocol contract

`Z8GitHub` shares `Z8Guest.commandFor()` with the terminal and uses `/z8/home`, normal guest `~/.config/gh`, the same source bind and guest toolchain. The process environment starts from an allowlist; Android-process `GH_TOKEN`, `GITHUB_TOKEN`, `GH_CONFIG_DIR`, XDG overrides, SSH agents, proxies and inherited Git redirects are not copied. Existing credentials created inside this project's guest remain available through gh's normal configuration. PRoot remains environment separation, not a security boundary between hostile same-UID programs.

Read operations use fixed `gh api --hostname github.com --method GET` commands with an explicit endpoint delimiter and the `2022-11-28` REST API version. Repository identifiers, issue/PR numbers, commit SHAs and page numbers are validated. Search text is URL-encoded as one query value. Neither user input nor response data becomes shell syntax, an arbitrary endpoint, a browser navigation or an executable command. HTTPS endpoints and remote HTML/Markdown are never evaluated by a WebView.

Read subprocesses have a 30-second execution limit and 1 MiB caps on stdout and stderr through the shared bounded process runner. JSON must be UTF-8 and is prechecked for nesting before Android's platform `org.json` parser runs. Decoded data is bounded by nesting/node count and a maximum of 30 list entries. Bodies render as selectable plain text, with display length caps. Very large responses fail visibly; they do not become fabricated empty results. Error messages classify common authentication/permission/not-found failures without rendering raw CLI stderr, which could contain sensitive data.

The structured REST path intentionally avoids requiring newer `gh auth status --json` or `gh pr checks --json` flags than the guest's Ubuntu package may support. Authentication and resource reads both validate structured JSON. Exit status alone never establishes a logged-in account. The [gh api manual](https://cli.github.com/manual/gh_api) documents the explicit method and raw endpoint behavior, and the [gh auth status manual](https://cli.github.com/manual/gh_auth_status) describes its exit codes and token-display option, which this UI never enables. Data models follow the official [check runs](https://docs.github.com/en/rest/checks/runs#list-check-runs-for-a-git-reference), [commit statuses](https://docs.github.com/en/rest/commits/statuses#get-the-combined-status-for-a-specific-reference), [repository search](https://docs.github.com/en/rest/search/search#search-repositories) and [Actions runs](https://docs.github.com/en/rest/actions/workflow-runs#list-workflow-runs-for-a-repository) endpoints.

## Integration and evidence

The auth intent targets `TermuxActivity` with `CLEAR_TOP | SINGLE_TOP` and these extras:

```text
Z8GitHubActivity.EXTRA_AUTH_SESSION = project.id
  literal key: dev.devsigner.z8.GITHUB_AUTH_SESSION
Z8WorkspaceActivity.EXTRA_PROJECT_ID = project.id
Z8Guest.EXTRA_GUEST_SESSION = true
```

The receiving route must validate matching project IDs and the private guest route before selecting its fixed auth entrypoint. It must not accept an external command extra. Workspace, manifest and Termux route integration are owned by the main implementation task.

`tests/test_github.py` compiles the actual pure-Java helper and exercises recorded REST fixtures plus a capturing subprocess runner. It verifies guest argv/environment construction, literal query handling, fixed GET/host behavior, credentials exclusion, auth output suppression, unavailable-runtime failure, request and response bounds, issue/PR separation, incomplete search, check state distinctions and malformed payload rejection. Clone fixtures additionally test hidden/dangling-file and source-link rejection, fixed clone argv/helper scoping, the two process budgets, duplicate prevention with a recreated client, successful post-clone verification, nonempty-source refusal, partial-file preservation, sanitized failure state and rejection of a zero exit without `.git`. Draft fixtures verify JSON escaping, UTF-8 byte limits, branch/owner validation, default base/account preflight, exact stdin-only reviewed fields, one accepted POST, shared clone/draft leases, duplicate detection without POST, no write after failed reads or account changes, rejection handling, UNKNOWN state without replay, strict result URL validation and actual draft status. The test uses Gradle's already cached Gson only as a host JSON fixture decoder; the APK uses Android `org.json` and gains no Gson dependency. The test performs no GitHub account, network, login or remote mutation operation.

Host tests do not establish authenticated Android/PRoot compatibility. Device acceptance still requires installing gh, completing a user-authorized project login, opening an accessible repository, reading issues/PRs/checks/Actions, testing denied/expired credentials and network interruption, and comparing results with the terminal's same project account. Clone acceptance additionally needs a user-selected small public repository with absent gh and with installed-but-unauthenticated gh, rotation immediately after confirmation and during clone, actual resulting files/origin/worktree validation, rejection of a nonempty project and an interrupted/failed-clone inspection. Draft creation requires a separately authorized test repository/branch pair and a real confirmation, followed by returned-PR validation, rotation and duplicate/unknown-result checks. Issue-to-local-branch and whole-PR review submission now have native controls and bounded backend tests; they still need authenticated Android acceptance in a user-selected test repository. No external GitHub write was performed by these host tests. Issue creation, inline review comments, merging, rerunning Actions and repository settings remain outside this increment.

## Audit regression coverage (2026-10-05)

The fixture suite now rejects zero-exit auth output without a valid user object, missing/fractional account IDs, and credential-bearing or foreign origin URLs; it separates 401, 403/rate-limit and network uncertainty. New fixtures verify literal PR patches, missing binary patches, review states, exact stdin payloads, changed account/HEAD/closed-PR refusal before POST, confirmed response validation, shared operation leases, uncertain outcomes, and absence of replay. The real Git suite continues to exercise branch creation/switching, dirty/stale-state refusal, and actual commits against temporary host repositories. Host tests run without GitHub credentials, network access, or remote writes. Activity persistence, compact layout and project-login round trips require APK validation in addition to these fixtures.
